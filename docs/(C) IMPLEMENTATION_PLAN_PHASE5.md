## Context

Tarek tested the shipped Phase 4 UI in the browser and found 12 real issues/requests spanning layout, navigation, interaction polish, and one new content feature (card titles + labels). Rather than one big undifferentiated fix pass, this becomes a new **Phase 5 ("Fix Iterations")** in `docs/(C) ROADMAP.md`, split into sub-phases exactly like Phase 4 was — each sub-phase is independently buildable and goes through this project's standard qa-subagent + code-reviewer-subagent convergence loop before the next starts. The current Phase 5 ("Cost/quality pass + friends testing") is renamed **Phase 6**, content unchanged, moved after the new Phase 5's "Done when."

Three genuine open decisions were resolved with Tarek before finalizing this plan:
- **Run-differentiation UI** (item 11): a run **divider** (thin rule + label between generation runs) — recommended option, chosen over tint/badge/section-headers.
- **Label taxonomy** (item 9's labels): **free-form, LLM-generated** tags, colors assigned via a deterministic hash-to-palette function — no curated list to maintain.
- **Legacy uniform-sizing diagnosis** (item 12): confirmed root cause is pre-severity-grading history rows (before commit `7976306`) defaulting to tier `"small"` via `rowToCard()`'s `severity ?? 1` fallback — **no code fix**, document only.

### 5.1 — Topic-band centering + grid full-width packing fix (+ legacy-sizing diagnosis, documented) — **DONE**

**Status: shipped and committed (`cceb648`).** Topic band centered; `PageGrid.tsx`'s CSS `grid-auto-flow: dense` replaced by an explicit JS pre-pass, `src/lib/packGrid.ts`, computing literal grid positions per card and widening the last card in a row/band to close any leftover width. Went through 3 full qa/code-reviewer rounds and two full rewrites of the algorithm before converging (see `notes-logs/session-log.md`'s 2026-08-06 entry for the detailed history — two structurally distinct gap bugs were found and fixed in the first two attempts, leading to a final "band" model: cards are stable-sorted by tier, then packed into a strict sequence of same-tier bands, each closed by widening its last card before the next band starts, so no band ever shares rows with a different band). Legacy uniform-sizing diagnosis (item 12) documented in `ROADMAP.md`, no code fix needed (confirmed inert pre-severity-grading history data, not a live bug).

**5.1 follow-up fix — restructure the tier system itself, not just the packing algorithm — DONE.** After shipping, Tarek looked at a real 6-story front page and identified a real design gap the packing fix alone couldn't solve: the *tier system* itself (`hero`/`large`/`medium`/`small`, mixed row-heights) was what made a lone "large" card get widened to full hero-size in the first place (the accepted trade-off documented in 5.1's roadmap entry). Rather than add vertical-stacking logic to accommodate mixed heights, the simpler and more robust fix is to remove the height variance entirely.

**Status: built, went through 3 qa/code-reviewer rounds, shipped locally — then corrected after Tarek reviewed the live result and caught a real misreading, with one more full qa/code-reviewer round on the correction. Fully converged; still uncommitted (sits on top of 5.1's `cceb648`) as of this doc's last update.** The first build gave every tier (`hero`/`medium`/`small`) `rowSpan: 2`. That was wrong: Tarek's own clarifying answer only ever said "double height" for hero and the middle tier (2-5) — the bottom tier ("the rest," 6+) was never described as double-height, and should have stayed the original single-row height. The misreading came from a question that grouped "ranks 2-6" into one bucket, then carrying "same height as hero" forward onto all of it instead of parsing the three distinct shapes Tarek actually described. Corrected — see the "Correction" subsection below, now applied and verified.

**New tier design (confirmed with Tarek across several rounds of clarification, corrected once after live review):**
- `GridTier` drops from 4 values to 3: `"hero" | "medium" | "small"` — `"large"` is deleted entirely (type, `TIER_DIMENSIONS` entry, `TEXT_CLASS` entry, `TIER_ORDER` entry — dead code removed, not left in place, per this project's convention).
- **Hero and medium are `rowSpan: 2`; small is `rowSpan: 1`.** Mixing row-heights across tiers is safe here specifically because the band model (already hardened through this session's earlier rounds) guarantees every band is 100% one tier, fully closed, before the next band starts — small always forms its own separate band(s), never sharing rows with hero/medium, so the earlier bug class (different-height tiers *sharing* a band) can't recur just because two different rowSpan values exist in the table.
- **Front page** (`tierForFrontPageRank`, rank 1-6 from `rank.ts`): rank 1 → hero (always alone, full width, 2 rows — required, not incidental). Ranks 2-5 → `medium` (colSpan 3 nominal, rowSpan 2 — pairs 2-per-band under the normal 4-medium count: ranks 2+3 share a band, ranks 4+5 share a second band). Rank 6 (and beyond, if the cap ever changes) → `small` (colSpan 2 nominal, rowSpan 1 — 3-per-band, which Tarek confirmed he's fine with). Confirmed exactly by Tarek, not a proposal.
- **Topic pages** (`tierForSeverity`, severity 1-5, topic-relative): mirrors the same 3-tier philosophy — proposed breakpoints (Tarek confirmed "same for other pages" in principle but didn't specify exact severity cutoffs): severity 5 → hero, severity 3-4 → medium, severity 1-2 → small. Flagged as a proposal, easy to adjust later.
- **Hero must never share a band with anything else**, even a same-width "medium" card, or another hero-tier card. `packGrid.ts`'s band-boundary check keys off **tier identity**, not row-height (`ordered[i].tier === bandTier`) — a real requirement given hero and medium now share the same rowSpan. Hero also has an explicit `maxPerBand: 1` on its `TIER_DIMENSIONS` entry (added in round 1 of this sub-phase's review loop — see below), since tier identity alone doesn't stop two hero-tier cards from packing side by side.
- **Known, accepted, milder edge case:** if a day's front page has fewer than the usual 4 medium-tier cards (e.g. only 3), the odd one out lands alone in its band and widens to full width — rendering the *same size* as hero (both full-width, 2 rows), though always positioned in a later row. Strictly milder than the trade-off originally accepted in 5.1's first ship (previously a lower-ranked card could render *bigger* than hero; now the worst case is *equal*, never bigger, always later in reading order). Documented in `ROADMAP.md`, not designed around.

**Files:**
- `src/lib/gridTiers.ts` — `GridTier` type; `TIER_DIMENSIONS` (hero `{colSpan:3, rowSpan:2, maxPerBand:1}`; medium `{colSpan:3, rowSpan:2}`; small `{colSpan:2, rowSpan:1}`); `tierForFrontPageRank`/`tierForSeverity` with the breakpoints above.
- `src/lib/packGrid.ts` — `TIER_ORDER` drops `large`; band-boundary condition keys off tier identity + `maxPerBand`; doc comment explains both rules and why mixing rowSpan values across (never within) bands is safe.
- `src/components/newspaper/NewsCard.tsx` — `TEXT_CLASS` loses `large`; `medium` doubled (2-row box); `small` stays at its original 1-row values.
- `src/lib/__tests__/gridTiers.test.ts`, `src/lib/__tests__/packGrid.test.ts` — rewritten for the 3-tier system: hero always alone even adjacent to a same-width medium *and* adjacent to another hero; medium pairs 2-per-band under the normal 4-count; an odd (3-count) medium scenario isolates the leftover; a parametrized no-merge check across every tier pair; small packs 3-per-band; a mixed-row-height regression test. Kept the existing `assertNoTrailingGaps`/`assertFullOccupancy`/`assertNoOverlaps` helpers.
- No changes needed to `FrontPage.tsx`, `TopicPage.tsx`, or `PageGrid.tsx` — none reference tier names as literals, only call the two mapping functions and pass results through.

**Process followed:** a full fresh qa/code-reviewer round ran on the initial tier restructure (round 1 found the hero-can-share-with-another-hero gap, fixed via `maxPerBand`; round 2 clean, including qa's 20,000-case fuzz run; round 3, scoped to a `maxPerBand` table-driven refactor suggested by code-reviewer, came back PASS/PASS WITH NOTES). A separate full round ran on the height correction specifically (both agents independently found only a stale-doc-comment issue — no functional bugs; `code-reviewer` proved the row-advancement arithmetic is safe since bands are always emitted in non-increasing rowSpan order per the stable pre-sort; `qa` exhaustively checked all 243 tier sequences up to length 5 plus 5,000 fuzz cases plus two live digest generations, zero failures). 96 vitest tests, `tsc`/`eslint` clean throughout. ### 5.6 — Dynamic summary-fill (replace fixed `line-clamp-N` with measured clamping)

**Files:** new `src/hooks/useDynamicLineClamp.ts`, `src/components/newspaper/NewsCard.tsx`.

Replaces the static per-tier `TEXT_CLASS` map (fixed line-clamp values, deliberately conservative today) with a hook that measures real remaining vertical space. Approach: on mount + via `ResizeObserver` on the card's fixed-height tier cell, compute `availableHeight = containerHeight - sum(reserved row heights: meta row, title row, label-chip row from 5.5, button row)`, divide by the summary element's computed `line-height` to get `clampLines = Math.max(1, Math.floor(availableHeight / lineHeight))`, apply via inline `WebkitLineClamp` style instead of a static Tailwind class. Keep tier-driven font-size classes unchanged — only the line-count is now dynamic. Direct division over binary search as the first implementation; fall back to a `scrollHeight`-vs-`clientHeight` check only if live testing shows drift.

**Hard dependency on 5.5** (must measure against the final title/chips layout, not redo the pass twice). Real risk: `ResizeObserver`/DOM measurement is a classic SSR hydration-mismatch source — render a safe static fallback on first paint, apply the measured value only after a client effect runs, mirroring how `NewsCard.tsx`'s `hasToggledBookmark` already handles the same class of problem in this file.
