# (C) Roadmap — Personalized News Aggregator

Phased build plan. **MVP end-to-end before polish** — each phase should leave you with something real and runnable, not a half-finished piece. Living document — expect revisions as building reveals reality.

---

## Phase 0 — Scaffold the real thing

- `git init`, GitHub repo, first commit (scaffold + these design docs).
- Next.js app created, deployed to Vercel — even an empty "hello world" page, live on a real URL.
- Supabase project created and connected.
- **Done when:** you can visit a real deployed URL and see something, however trivial.

## Phase 1 — Prove the core pipeline (hardest part first, no auth yet)

- Hardcode one dev profile (your own topics + preferred sources) — no login screen yet.
- Build the full pipeline: RSS ingestion → embedding-based clustering → Haiku triage → Sonnet card writing → render as a scrollable feed.
- No calendar history, no bookmarking, no ad-hoc chat requests yet — just: request a digest, get real cards back, for one hardcoded set of topics.
- **Why this before auth:** this is the actual novel/risky part of the product — whether the synthesis pipeline produces genuinely good, notable, well-written cards. Proving that cheaply (without spending time on login screens) tells you fast whether the core idea works before investing in anything else.
- **Done when:** you personally get a real "give me today's news" digest, end to end, with real cards from real sources.

## Phase 2 — Real accounts

- Wire in Supabase Auth: real signup/login screen.
- Profile setup flow: curated multi-select for topics (at least 1, no upper bound), curated multi-select for preferred sources.
- Replace the hardcoded dev profile from Phase 1 with real per-user preferences driving the same pipeline.
- **Done when:** you can sign up, pick your topics/sources, and get a digest driven by your actual profile — not a hardcoded one.

## Phase 3 — History and bookmarking

- Persist each day's digest so past days are retrievable; add a history view to browse them.
- Same-day generation is additive, not duplicate-or-replace: one `digests` row per user per calendar date, appended to across multiple runs that day (server-owned `last_generated_at` cursor replaces the old client-`localStorage` one) rather than creating a second digest or silently redoing the whole day.
- Add bookmarking: a join table linking a user to a card ID, plus a "Saved" view.
- Also shipped alongside this phase (not originally scoped here, but the natural moment for it — see "Explicitly deferred" below): the lazy expanded-report generation described in `ARCHITECTURE.md`/`TECH_STACK.md`, since cards only got real persistent IDs to cache it against in this phase.
- **Done when:** you can revisit yesterday's digest via the history view, and bookmark a card and find it again later in Saved.
- **Built as:** a simple reverse-chronological date list, not a real calendar-grid widget — see "Explicitly deferred" below.

### 5.1 — Topic-band centering + grid full-width packing fix

Center `TopicBand`'s topic list (currently left-aligned). Diagnose and fix story boxes not consistently filling the full page width: `PageGrid`'s CSS `grid-auto-flow: dense` reorders later items into exact-fit gaps but never resizes an item to close a leftover gap, so mixing row-span-1/row-span-2 tiers can leave a trailing row underfilled.

Replaced CSS auto dense-placement with an explicit JS pre-pass, `src/lib/packGrid.ts`. Went through **3 full qa/code-reviewer rounds**, the first two each finding a real, structurally distinct gap bug in a "widen the last item placed in a row" occupancy-bitmap design: round 1 found out-of-order tier input (a rowSpan-1 card before rowSpan-2 cards) could leave a mid-row hole nothing could reach; round 2 found that even with correctly-ordered input, a rowSpan-2 card's *second* row could be left uncovered when its first row got exactly consumed by trailing rowSpan-1 cards — a grid item can't be widened on only one of the rows it spans without overlapping different content already in the other. Given two structurally similar bugs from the same patch-a-special-case approach, the function was redesigned rather than patched a third time: items are stable-sorted by tier (hero/large before medium/small, preserving each card's relative import­ance order within its own tier), then packed into a strict sequence of "bands" — a run of same-rowSpan cards filling a fresh, exclusive set of rows, closed by widening its last card before the next band starts. Because a band never shares a row with a different-rowSpan band, cross-rowSpan bleed-through (the root cause of both prior bugs) can't occur at all — gap-free by construction, not by special-casing. Round 3 (fresh, both agents) found no correctness issues, including under `qa`'s own 3,500+-case fuzz run and live-generated real digests.

**Trade-off, initially put to Tarek and accepted as-is, then superseded (see follow-up below):** the band model couldn't let different-row-height cards interlock within the same physical row, which could produce a visual hierarchy inversion on a full 6-story front page — a rank-3 card left alone in its own row-span-2 band got widened to full page width and full hero height, rendering more prominent than the rank-1 hero. Initially accepted rather than reintroducing a partial gap to cap it — but after seeing a real front page, Tarek decided a better fix existed than living with the trade-off (see below).

- **Done (2026-08-06):** topic band centered (`justify-center`); grid full-width packing fixed via `src/lib/packGrid.ts`'s band-based algorithm; legacy uniform-sizing finding documented above. 94 vitest tests (up from 88), `tsc`/`eslint` clean, 3 full qa/code-reviewer rounds to genuine convergence (rounds 1-2 each found and fixed a real bug; round 3 clean from both agents plus qa's own 3,500+-case fuzz run). One non-blocking trade-off surfaced to Tarek and accepted, documented above.

**Follow-up (2026-08-06, same day) — 3-tier restructure, replacing the accepted trade-off with a structural fix.** After looking at a real 6-story front page, Tarek proposed removing the height variance that caused the trade-off in the first place, rather than living with it: `GridTier` drops from 4 values to 3 (`"hero" | "medium" | "small"` — `"large"` deleted entirely, dead code removed not left in place). Front page (`tierForFrontPageRank`): rank 1 → hero, always alone; ranks 2-5 → medium (normally 4, pairing 2-per-band); rank 6 → small. Topic pages (`tierForSeverity`): severity 5 → hero, 3-4 → medium, 1-2 → small (Tarek confirmed the same philosophy for topic pages, breakpoints are a proposal). **Hero and medium are 2 rows tall; small is 1 row tall** (see the Correction below — the first build wrongly made all three 2 rows tall). Real 6-card front page now renders exactly as intended: hero alone (2 rows) → medium pair (2 rows) → medium pair (2 rows) → small alone (1 row, visibly shorter), all full width, verified live.

Needed one substantive algorithm change in `packGrid.ts`: band boundaries, which used to key off row-height (rowSpan) equality, had to key off **tier identity** instead, since every tier now shares the same rowSpan and rowSpan-based boundaries would no longer distinguish tiers at all (hero + medium would merge into one band whenever width allowed, e.g. hero's nominal colSpan 3 + medium's colSpan 3 = an exact 6-width fit). Went through **3 more full qa/code-reviewer rounds**: round 1 (code-reviewer and qa both independently) found tier-identity alone wasn't sufficient — two hero-tier cards could still merge into one band (reachable on topic pages, where severity ties have no per-topic uniqueness guarantee, unlike the front page's deduplicated rank), since hero's own nominal width let two of them fit exactly. Fixed by capping a hero band at exactly one card, later refactored (per code-reviewer's suggestion, adopted since this codebase has a documented pattern of narrow fixes recurring — see the 2026-08-05 B6/B7/B8 `inert` entries) from a hardcoded `if (bandTier === "hero") break` into a table-driven `maxPerBand` field on `TIER_DIMENSIONS`, so the constraint is visible next to the tier's other properties rather than buried in the algorithm. Round 2 (both agents, including qa's 20,000-case fuzz run) came back clean. Round 3 (both agents, scoped to the `maxPerBand` refactor specifically) came back PASS/PASS WITH NOTES — one trivial, non-blocking note (both reviewers independently: an unenforced `maxPerBand >= 1` invariant would crash, not hang, if a future tier ever violated it) — addressed directly with a defensive guard rather than spinning a fourth full round for a one-line addition both reviewers had already endorsed the direction of.

**Known, accepted, milder edge case (documented in `packGrid.ts`'s own comment):** if a day has an odd count of a tier (e.g. 3 medium cards instead of the usual 4), the leftover renders alone at full width — the same *size* as hero, though always positioned in a later row. Strictly milder than the original trade-off (previously a lower-ranked card could render *bigger* than hero; now the worst case is *equal*, never bigger, always later in reading order) — not designed around, just documented.

96 vitest tests (up from 94), `tsc`/`eslint` clean throughout. Test accounts created during this follow-up's live verification and qa passes, flagged for manual Supabase cleanup: `pna-tiers-test+...@example.com`, `qa-pna-51-1786045337116@example.com`.

**Correction (2026-08-06, same day, after live review) — small reverted to 1-row height.** Tarek reviewed the shipped result and caught a real misreading: his original clarifying answer only ever said "double height" for hero and the medium tier — the bottom tier ("the rest," 6+) was never described as double-height and should have stayed single-row. The build had wrongly given all three tiers `rowSpan: 2`. Root cause: a clarifying question that grouped "ranks 2-6" into one bucket, then carrying "same height as hero" forward onto the whole bucket instead of parsing the three distinct shapes actually described. Fixed: `TIER_DIMENSIONS.small.rowSpan` reverted to `1` (hero/medium stay `2`); `NewsCard.tsx`'s `TEXT_CLASS.small` reverted to its original 1-row values. No change needed to `packGrid.ts`'s core algorithm — the tier-identity band-boundary rule already guarantees every band is single-tier and exclusive-rows, so mixing rowSpan values *across* bands (hero/medium at 2, small at 1) is safe by the same invariant that was already built and verified; only the *documentation* had drifted to claim "every tier is the same height," which was corrected in `packGrid.ts`'s and `packGrid.test.ts`'s doc comments too. One full qa/code-reviewer round on the correction: both agents independently found the identical stale-doc-comment issue (no functional bugs) — `code-reviewer` traced the row-advancement arithmetic (`currentRow += bandRowSpan`) precisely and confirmed it's safe because bands are always emitted in strict non-increasing rowSpan order (hero/medium always precede small, per the stable pre-sort), so a "short band followed by a tall band" transition is architecturally unreachable; `qa` exhaustively enumerated all 243 tier sequences up to length 5 plus 5,000 random fuzz cases, zero failures, plus two full live end-to-end digest generations confirming small rows render at exactly half the height of hero/medium rows with clean transitions in both directions. 96 vitest tests (one new regression test added, `"gives hero and medium double-row height but small a single row, mixed within one page"`), `tsc`/`eslint` clean.

### 8.3 — Full report shouldn't generate just from opening focus mode

### V2.0 — BLOCKING DECISION: who pays for the Claude API, and how keys are handled

> **This is a hard gate, not a task.** Nothing ships to another human being — not a deploy link, not the repo — until this is decided and the chosen option is built and tested. It determines whether a credential-storage subsystem exists in this codebase at all, so deciding it late means building V2.1 twice. Decide it **after** the Final Phase produces the real per-digest cost figure (that number is what makes Option B's caps sizable) and **before** writing any V2.1 code.

**The problem.** The app calls the Claude API on every digest generation. Someone's account gets billed. Today that's Tarek's key in a local `.env.local` and the question never comes up — the moment a second person can generate a digest, it has to be answered.

#### The security reality that shapes the whole decision

**A user's API key cannot be fully secured by any storage scheme.** The server must hold the plaintext key at the moment it calls Anthropic — that is inherent to being the party making the call, not a flaw to engineer around. Encryption at rest therefore protects against exactly one scenario: a database dump with nothing else compromised. It does **not** protect against a compromised server, a leaked environment variable, a malicious or compromised npm dependency, or an ordinary bug that logs a request body.

And the asset in question is a credential that spends someone else's money with no inherent limit. A leak costs Tarek's friends real money and it is Tarek's fault. That asymmetry — unbounded liability, irreducible risk — is the reason Option B is recommended over Option A, not any implementation detail.

---

#### Option A — Bring-your-own-key (users supply their own Anthropic key)

Each user pastes their own key; the app stores it and uses it for their generations. Tarek pays nothing.

**If chosen, the design is non-negotiable on these points:**

- **Encrypt at rest with AES-256-GCM**, the encryption key held in a Vercel environment variable — **never** in the database alongside the ciphertext. Alternatively use **Supabase Vault**, which is purpose-built for this and keeps key management out of application code.
- **Store keys in a table the publishable/anon key cannot reach at all** — service-role access only. An RLS policy is not sufficient isolation for this class of secret; the client should have no path to the row, correct policy or not.
- **Never log the key, never return it to the client** (not even masked-with-reveal), and never let it reach an error tracker or exception report. Store a last-4 fingerprint separately for UI display.
- **Give users visible delete and rotate paths**, and state plainly in the UI that Tarek's server holds their key.
- **Verify Anthropic's terms** on third-party applications accepting end-user API keys before shipping this. To be confirmed against current policy, not assumed.
- **Smallest-blast-radius variant, if Option A is chosen at all:** don't persist the key server-side. Hold it in an encrypted `httpOnly` session cookie and re-prompt each session. Worse UX, dramatically less to lose in a breach.

**Costs of this option beyond the security burden:** it reintroduces the exact adoption barrier deployment was meant to remove — "create an Anthropic account, add a credit card, generate a key, paste it here" is a wall most testers will not climb, and those who do are paying to test Tarek's app. It is also strictly more code than Option B.

**When Option A actually makes sense:** a public launch with more users than Tarek can fund. It is a scaling answer, not a friends-testing answer.

---

#### Option B — Tarek's own key, server-side only, with hard spend caps **(recommended)**

Tarek's key stays in a Vercel environment variable and never leaves the server. Users sign up and use the app. **There is no user credential to store, so the entire security question above ceases to exist** — nothing to encrypt, nothing to leak, no liability.

Cost is controlled by four independent mechanisms, all small to build:

1. **Invite-only signup** — email allowlist or invite codes. Tarek controls exactly who can exist as a user. This is the primary cap; everything else is defense in depth.
2. **Per-user daily digest limit** — one per day matches the natural shape of a daily news product, so it costs nothing in UX.
3. **An Anthropic Console budget cap** — a hard backstop enforced outside the application, so an application bug cannot run up an unbounded bill.
4. **A kill-switch environment variable** that disables generation without requiring a redeploy.

**Why this is sizable in advance:** with invite-only signup and a daily limit, worst-case spend is arithmetic that can be checked before deploying — (number of invited users) × (1 digest/day) × 30 × (real per-digest cost), plus expands.

**The real numbers, measured at the close of the Final Phase (2026-08-15), corrected for pricing 2026-09-11:** **\$0.335 per digest**, plus **~\$0.012 per card expanded**. Ten invited users at one digest a day is **~\$100/month** at full daily usage, not the \$60 this line assumed — and the original assumption of a \$0.20 digest was itself ~10× under the then-real cost of \$1.94 before optimization. Expands are not a rounding error: a user who opens ten cards a day adds ~\$0.12/day, roughly another half-digest each, so a cap on digests alone does not bound spend.

Three things to carry into the actual sizing rather than re-deriving them:

- **There is no longer an at-list column, and the instruction that used to be here was inverted.** It read: "Use the at-list column. Sonnet introductory pricing ends 2026-08-31; after that at-list is the bill. Sizing off the billed figure would under-provision by ~19%." Anthropic cancelled that increase on 2026-09-01 and made \$2/\$10 Sonnet 5's standard price, so the billed figure was correct all along and at-list would have **over**-provisioned by ~19%. One number, one column. Re-verify published rates before sizing anything; `PRICING_VERIFIED_ON` in `src/lib/usage.ts` records when that was last done.
- **The cold/warm framing this bullet used to carry was wrong, and the run-shape labels in the code are what made it wrong.** It read: "\$0.335 is a cold-start number — first run of a new account... A returning daily user ingests roughly half as much and costs materially less. Sizing off \$0.335 overestimates, probably close to 2×." **That is not supported by any measurement, and the mechanism argues against it.** The since-cursor reduces how many articles are *ingested*, and ingestion is free — RSS fetching and local embedding cost \$0. Every billed dollar is triage, writeCard and rank, which scale with clusters and cards written, not with articles fetched. Two runs at full config bear this out: 2026-09-11 ingested 1280 articles and wrote 91 cards for \$0.450229; 2026-09-14 ingested 1147 and wrote 87 for \$0.471763 — **10% fewer articles, 4.8% more money.** Those two runs are not a warm/cold comparison at all, though: the first had a null cursor and the second a three-day-stale one, so **both ingested a saturated 48h window** and the difference between them is news volume. **The true recurring daily figure remains unmeasured.**

- **Blocking the cap sizing: `deriveRunShape` throws away the one input the cap needs, and its labels invert the product's own vocabulary** (found 2026-09-14). The classifier is internally correct and well documented — `cold` means no successful generation has *ever* run for this user, `warmNewDay` means the first run of a new day, `warmSameDay` a second-or-later run today. But three things follow that the cost report does not survive. **First, `cold` is a once-per-account-lifetime event** — an onboarding cost, not a baseline, yet `usageRecord.ts`'s own header still says "every cost number in this project's docs came from a COLD run" as though that were the norm. **Second, `warmNewDay` is what this product calls a normal daily brief** — the first generation of the day, the main recurring cost — and it is labelled as though it were an incremental top-up. In the product, a day opens with a fresh brief and *Complete Today's Brief* tops it up; those are the words that should appear on a cost report, and the code's do not. **Third and worst: the classifier reads `sinceIso` as a null/non-null signal only and never parses its contents, so cursor age is discarded.** A `warmNewDay` after 24 hours and one after three days differ enormously — the 48h lookback ceiling saturates somewhere between them — and both land in the same bucket and the same mean. **That discarded number is exactly what a per-user cap consumes.** The fix before any cap is sized: rename to the product's vocabulary (`firstEver` / `firstOfDay` / `sameDayTopUp`), record cursor age in hours as its own field, and correct the module header's claim. It touches the money path, so it goes through the full qa/code-reviewer loop rather than landing as a drive-by.

- **Cap expands separately from digests**, or the digest cap doesn't bound anything.

**Trade-off, stated honestly:** Tarek pays for other people's usage. That is the entire downside, and it is bounded by construction.

#### V2.1.2 — Spend caps that actually bind

The mechanism from the capping session. A **server-owned counters/ledger table with no authenticated write policies**, written only through database functions that move counts and dollars **upward**, so the subject of a cap cannot lower it. Generation **reserves a worst-case amount before the pipeline starts**, sized from the profile's breadth, and settles to the real figure afterwards — a run killed mid-flight therefore keeps its reservation and fails closed, which is the hole that post-hoc recording in `usage_runs` cannot close (see the log's 2026-09-14 night entry).

Caps: a **per-user daily dollar budget** as the real bound, with **3 top-ups** and **15 expands** per day as guardrails above it; a **global daily dollar breaker** across all users; a **kill-switch environment variable** that stops generation with no redeploy; and an **Anthropic Console monthly spend limit on a workspace dedicated to production**, which is the only backstop enforced outside this codebase.

`usage_runs` keeps its job — it **sizes** the caps and is never what enforces them.

- **Plan-mode scope:** the table shape and which functions may write it; how a reservation is sized from topic/source counts (and what the 2026-09-15 cost run changed about that); the per-user daily budget number and the global daily number; reservation settlement, including a run that never returns; what the user is shown at each cap and when it resets; how the kill switch is read; and how each cap is **tested to actually block**, which V2.0's done-condition requires by name.
- **Done when:** a user at their cap is refused generation with a clear message and a reset time; a killed run still consumes its reservation; the global breaker and kill switch are both demonstrated stopping generation; and the Console limit is set.

**Planned 2026-09-17 — what changed from the text above.** Four decisions from plan mode supersede parts of this item:

- **Limits are a rolling 24 hours, not a calendar day.** \$2.00 per user and \$10.00 globally in any 24 hours, plus 4 digest runs (the first and 3 top-ups) and 15 expands. #### V2.3.x (deferred) — Triage is half the bill, and the card cap cannot touch it

**Deferred by Tarek 2026-09-21, out of V2.1.4's scope.** V2.1.4 tiered the per-topic card cap, which bounds `writeCard`; it cannot reduce triage, because triage runs *before* the cap and has already been paid for on every cluster the cap discards. Triage is the largest stage and the levers for it are a different design, recorded here with the arithmetic so none of it is re-derived.

Baseline, from the 2026-09-17 production run: **triage \$0.1177 of \$0.231078 (51%)** across ~30 batched Haiku calls of ~2,298 input tokens each, ~700 of which is fixed prompt. 559 clusters were judged to keep 38 cards. Triage cost is invariant to verdicts — a reject bills the same as a pass — and scales with *clusters*, not cards.

Levers, largest first:

- **Route triage through the Batch API by pre-generating on a schedule — about −50%, and the same on `writeCard` and ranking.** The Batch API is half price but asynchronous, so it cannot be used inside a 62-second interactive request. A newspaper is printed before its readers wake up; generating the daily digest on a schedule rather than on a button press would make the whole pipeline eligible, taking triage to roughly \$0.059 and halving the digest. The largest lever and the biggest change — it interacts with V2.1.7's definition of "today", and it changes the product's interaction model, so it is a product decision as much as a cost one.
- **Pre-select candidates before triage — up to −79% of triage (~\$0.093, 40% of the digest).** Embeddings are already computed for clustering, so a local signal (cluster size, recency, source diversity) is free. Triaging only ~3x the per-topic allowance instead of every cluster would cut it to about \$0.024. The real risk is that the proxy is not notability: a single-source scoop could be the day's biggest story and would be cut before anything judged it. Shares its lever with V2.1.11, so they belong in one conversation.
- **Shorten the per-article snippet clip below 200 characters — about −16% of triage.** The snippet is roughly 77% of the variable tokens. Needs the same real-model quality check V2.1.3 ran on the clustering clip, comparing verdicts rather than asserting they hold.
- **Raise the triage batch from 20 clusters to 40 — about −9% of triage.** Halves the call count to ~15 and with it the fixed-prompt share. Output is unchanged at one verdict per cluster. The existing split-retry ladder absorbs the added truncation risk.

**Two levers rejected with arithmetic. Do not revisit without new numbers:**

- **Prompt caching.** Haiku 4.5's minimum cacheable prefix is **4,096 tokens**, against a fixed prompt of ~700. Reaching it needs ~3,400 tokens of padding; one cache write at 1.25x plus 29 reads at 0.1x costs about \$0.017 against the ~\$0.021 paid today. That is **~\$0.004 a run, 3.4% of triage**, in exchange for paying to send filler. The cache minimum is not monotonic across model generations, so re-check it if the triage model ever changes — on a 512-token-minimum model this lever becomes live.
- **Capping the articles sent per cluster.** The 2026-09-17 run had 659 articles in 559 clusters — a mean of **1.18 articles per cluster**. Multi-article clusters are rare and there is almost nothing to trim.

- **Duplicate/near-duplicate story cards, if they persist after the best-match clustering fix** (surfaced during Tarek's first manual testing pass, 2026-07-30): `src/lib/cluster.ts`'s greedy clustering was changed from first-match to best-match (highest cosine similarity among all existing clusters clearing `SIMILARITY_THRESHOLD`, not just the first one found) to remove one concrete, order-dependent source of inconsistency. That fix does **not** address the deeper limitation: a single fixed similarity threshold (0.65) on embedding-only similarity can't cleanly separate "same story, worded differently across outlets" from "different but related stories" for every topic and every day's mix — same-story articles vary a lot in embedded similarity depending on wording overlap, cross-language pairs (e.g. a French-language Le360/Le Monde piece vs. an English source on the same event), snippet length, and how much of the RSS snippet is boilerplate vs. substance. Confirmed live (2026-07-30, 29-card European Football digest): the best-match fix is real but duplicates still occur — at least 3 clear same-story pairs stayed split (e.g. two separate cards both about Eddie Howe leaving Newcastle).

  Brainstormed with Tarek (2026-07-30) on next steps, ranked by confidence:

  - **Low confidence: retune `SIMILARITY_THRESHOLD` alone.** The code comment already shows real same-story pairs scoring as low as 0.70–0.777 while a known false positive scored 0.634 — a ~0.07 band where same-story and different-story genuinely overlap in embedding space. Moving the one threshold trades one failure mode for another (catch more real duplicates ↔ merge more unrelated stories); without the actual scores for the specific pairs still splitting, there's no guarantee a new threshold value would even catch them.
  - **Moderate confidence, real effort: add a secondary dedup signal** (e.g. named-entity/keyword overlap as a tiebreaker alongside embedding similarity). A legitimate, standard idea — shared specific names is a crisper same-story signal than sentence-embedding cosine similarity alone — but it's a real design change (needs its own extraction step, and a way to combine two signals sensibly; entity overlap alone isn't sufficient either, since two different transfers involving the same club would share an entity without being the same story).
  - **Recommended first thing to actually try: an LLM-based borderline check.** After embedding clustering runs, for any pair of clusters sitting near the threshold, ask Haiku directly "are these the same real-world story?" — the one mechanism that can actually *read and reason* about "same event, differently framed," rather than proxying it through embedding math or keyword counts. Reuses infrastructure already trusted elsewhere in the pipeline (tiered Claude usage, Haiku already does triage) rather than introducing a new one. Considered and ruled out: training a custom clustering/classification model — clustering algorithms like DBSCAN/agglomerative are unsupervised (no training data needed) so "train a model" isn't quite the right frame anyway, and a supervised approach would need a labeled same-story/different-story dataset that doesn't exist — disproportionate effort for this project's current stage. Swapping the greedy single-pass algorithm for a proper clustering algorithm (agglomerative/DBSCAN) is a smaller, second-order improvement worth doing too (removes remaining order-dependence), but the LLM check is expected to move the needle more.

- **Per-card "relevant / not relevant" user feedback, with a reason picker and a reversible removal** (raised by Tarek 2026-08-18, scoped for V2): every story card gets a relevance control. **"Relevant"** records a positive signal and nothing else changes. **"Not relevant"** opens a modal asking *why*, offering the failure modes this pipeline is actually known to produce — **duplicate of another card in today's brief** (the clustering/`dedup.ts` miss already tracked in its own deferred item above), **story isn't from the last 24h** (a stale-`since`-cursor or a feed republishing old items), **wrong or inaccurate information** (a synthesis error from `writeCard.ts`), and **other**, which reveals a free-text field. On submit the card is **removed from the digest**, with an undo path that restores it exactly as it was — position and `frontPageRank` included — since a misclick shouldn't cost the card.

  **The three things that need designing before any of this gets built, and none of them are the UI:**

  - **Where the feedback lives and what it's for.** A new table keyed on `(user_id, card_id)` is the obvious shape, but the *purpose* decides the columns: pure telemetry for Tarek to read (cheap, no pipeline change) is a different table from something that feeds back into triage or clustering (needs the reason enumerated, stable, and joinable to the cluster that produced the card). Decide which before writing the migration — retrofitting the second onto the first means a second migration.
  - **Removal semantics.** Is a removed card soft-deleted from the digest row, or is it filtered at render on a `dismissed` flag? Filtering is far safer for the undo requirement and for the fact that `rank.ts` re-ranks the **full cumulative pool** every run — a hard delete makes the card ineligible to return, and a later run could then re-add the same story as a "new" card, which is a worse bug than the one being fixed.
  - **Re-flow after removal, which is the genuinely hard part.** The front page isn't a flat list: `frontPageCardsOf`/`applyCardCap`/`rank.ts` produce a ranked layout where **rank 1 renders hero-sized**. Removing a card is therefore not "close the gap" — if the removed card is the hero, something has to be promoted into that slot, and the Phase 8.4 machinery already exists for exactly that shape (`applyRankUpdates` + the `pendingEntrances` one-shot entrance, which deliberately stops a promoted card from replaying its entrance animation). Reuse that path rather than inventing a second one. Also decide whether removal re-ranks at all or just vacates the slot — re-ranking on every dismissal makes the page move under the reader's cursor, which is the interaction complaint Phase 6.5 was already about.

  **Worth noting for scoping:** the negative-feedback reasons double as a free, user-labelled evaluation set for the triage prompt — the Final Phase had no ground truth to calibrate `triage.ts` against and had to fall back on distribution bands (severity ≥ 3 counts) as a proxy. This is the cheapest route to real labels the project has.

The framing is deliberate and worth keeping: this is a **refresh layered on v1's existing UI as the foundation**, not a redesign — the tokens, the newspaper identity and the component structure stay, and 21st-sourced components get restyled into them exactly as `UI_WORKFLOW` step 4 requires ("pull for behavior, not appearance"). Four things to know before scoping it:

### Track B — Correctness debt

Real defects, none currently user-visible in single-user local use, ordered roughly by how much they would matter once other people generate digests.

- **`planTriageBatches` reads `cluster.topic` unguarded, breaking `triageClusters`'s never-rejects contract** (found independently by three separate review rounds during F.4.7, 2026-08-14; pre-existing since F.4.5's batching restructure): it runs synchronously at the top of `triageClusters`, before any batching or retry machinery, so a null/malformed cluster anywhere in the input array makes the whole call **reject** rather than fail that cluster closed — for the entire digest, not just one batch. That contract is load-bearing: the digest route gave up its own per-cluster try/catch specifically to depend on it. Not reachable through today's ingest path, which is why it's deferred rather than urgent; the fix is to wrap the planning call in the same fail-closed pattern the rest of the module already uses.
  - _Status note, verified against the code 2026-09-14: still open — `planTriageBatches(clusters)` is still called bare at the top of `triageClusters`, and `triage.ts`'s own comment still records the hazard._

- **Cards land invisible when the tab is backgrounded during generation, and only a reload brings them back** (reported by Tarek 2026-08-18 after leaving the tab mid-generation; **diagnosed in code the same day and confirmed as a real defect**, not a one-off): switch to another browser tab while a digest generates, come back after it finishes, and the cards are not shown until the page is refreshed.

  **Root cause — the entrance-animation backstop timer and the animation it guards run on two different clocks, which only agree while the tab is visible.** The chain, traced through `DigestGenerationContext.tsx`, `NewsCard.tsx`, `entranceTiming.ts`, and `motion-dom`'s own source:

  1. The NDJSON stream is not rendering-gated, so the `done` event still arrives and `setCards`/`setPendingEntrances` still run in a hidden tab. The cards do enter React state — this is **not** a lost-state bug.
  2. Each new card mounts with `initial={{ opacity: 0, scale: 0.97 }}` and animates to `opacity: 1` (`NewsCard.tsx:333-334`). That animation is driven by Motion's frameloop, i.e. `requestAnimationFrame` — **which does not fire at all in a hidden tab.** The cards sit at opacity 0 and never progress.
  3. `DigestGenerationContext.tsx:274-284`'s backstop `window.setTimeout` is a **wall-clock** timer. Hidden tabs throttle it (≥1s, and ≥60s after five minutes hidden) but they do not stop it. It fires, deletes the batch from `pendingEntrances`, and `animateEntrance` flips to `false`.
  4. With `animateEntrance` false, `animate` becomes `undefined` and Motion **stops** the still-unfinished animation. `NativeAnimation.stop()` (`node_modules/motion-dom/dist/es/animation/NativeAnimation.mjs:77-91`) returns early only for `idle`/`finished` animations; for a running one it calls **`commitStyles()` and then `cancel()`** — writing the animation's *current* value, `opacity: 0`, into the element's **inline style** and then discarding the animation.
  5. Nothing ever clears that inline style. On return to the tab there is no animation left and no `animate` target, so the cards stay at `opacity: 0` permanently. A reload rebuilds the DOM from SSR with `animateEntrance` false from the start (`initial={false}`), so the cards render at their natural opacity — **which is exactly why refreshing is the only thing that fixes it.**

  **This is a known failure shape in this project, not a new one.** `entranceTiming.ts`'s own doc comment records that "a card retired while animating loses its `animate` target and freezes part-faded... is precisely the bug shape that broke Phase 8.4 twice," and `DigestGenerationContext.tsx:260-265` records a per-card variant that froze every card at opacity 0 in dev. The shared-constant fix made the timer strictly longer than the animation — a correct invariant **in wall-clock time**, and the unexamined assumption was that animation time and wall-clock time advance together. A backgrounded tab is precisely the case where they don't: one stops dead, the other keeps running.

  **Likely fix direction (not decided, and deliberately not implemented yet):** the backstop timer must not retire an entrance that has not actually had a chance to play. Options worth weighing — pause/restart the timer on `visibilitychange` so it only counts down while the document is visible; make retirement idempotent by having the retired state render at `opacity: 1` explicitly rather than relying on "no `animate` prop" meaning "whatever the element currently is"; or drop `initial`'s `opacity: 0` in favour of an entrance that is additive over a visible base, so a frozen animation degrades to a visible card instead of an invisible one. The last is the most robust — **it makes the failure mode "no animation" instead of "no content,"** which is the right direction for something that is only ever decorative.

  **One honest caveat, and a free way to close it:** this was diagnosed by reading the code and Motion's installed source, not by reproducing it in an instrumented browser. There is a zero-cost discriminator that needs no new digest generation — next time it happens, check whether the page shows the **"No edition yet today."** empty message or just blank space where the cards belong, and whether the topic nav is enabled (it is gated on `hasDigest`, so an enabled nav proves the cards reached state). Empty message + disabled nav would mean the state never arrived and this diagnosis is wrong; blank space + enabled nav, with `opacity: 0` visible on the card elements in DevTools, confirms it.

- **Pipeline error handling: side effects on a billed call's return path can silently discard paid work** (found by `qa` during the Final Phase's F.2 review loop, 2026-08-13; noted as deferred at Tarek's direction rather than fixed in that phase): `src/lib/triage.ts`'s per-cluster `console.log` and `src/lib/dedup.ts`'s per-exclusion `console.log` both run *after* their Claude call has resolved and been billed, unguarded. If either throws, the throw is indistinguishable from the API call itself failing, and each caller's existing error handling then does exactly what it's designed to do with a failed call — triage treats it as "not notable" and drops the cluster; `filterAlreadyCovered` falls back to un-deduplicated results. *(Written during F.2, when the digest route caught per cluster. F.4.5 moved that catch inside `triageClusters` and guarded `triage.ts`'s own log line, so the triage half of this entry is now fixed; `dedup.ts`'s remains open, and the category question below is unchanged.)* So a **genuinely notable, already-paid-for story can be silently dropped from the digest by a logging failure**, with the fail-closed convention hiding it.

  The same bug shape was found and fixed inside the cost instrumentation during that phase (`usageCollector.ts`'s `add`/`report` now guard their own logging, so instrumentation can't break the thing it measures) — these two predate it and were left alone because changing pipeline error handling is a real behavioral decision, not a drive-by. `console.log` throwing is admittedly rare in practice (a closed/broken stdout, a patched console, an exhausted process), which is why this is deferred rather than urgent.

  Worth treating as a category rather than two one-line fixes when it's picked up: the general question is which side effects sit on a billed call's return path, and whether the pipeline's fail-closed conventions should distinguish "the API call failed" from "something after it failed." A narrow fix is a `try/catch` around each log; a better one is deciding that anything after a successful billed call is best-effort by construction.

  - _Status note, verified against the code 2026-09-14: the triage half is fixed, as the entry's own parenthetical says; **`dedup.ts`'s unguarded per-exclusion `console.log` is the only part still open**, along with the category question._

- **`Controller is already closed` error under client-disconnect mid-stream** (surfaced incidentally by `qa`'s own test tooling during the Phase 4 final integrated pass, 2026-08-05, not a regression from that batch — pre-existing behavior in unrelated code): `src/app/api/digest/route.ts:244` throws a `TypeError` if the client aborts/disconnects (e.g. closing the tab) while the digest-generation stream is still actively enqueueing NDJSON events.   - _Status note, verified against the code 2026-09-14: **the entry's ask is already satisfied and its remaining defect is different.** The `controller.enqueue` call now sits inside `pull`'s `try`, with a nested guard on the error path, so a client disconnect no longer throws unhandled. - **Post-flip keyboard focus lands on Masthead, not new page content** (found by `code-reviewer` during Phase 4.4 Track B B8's round 3, 2026-08-05; explicitly put to Tarek and accepted rather than fixed): after a keyboard-triggered page-flip, `PageTransitionInertBoundary.tsx` moves focus to its own root (the wrapper around Masthead + page content) so it isn't left stranded on `<body>`. ### Track D — Product expansion

Genuinely new capability. Each needs its own scoping session; none is a drive-by.

- **Ad-hoc requests (chat-style topic queries), deferred out of the numbered phases** (was Phase 4, moved here 2026-07-31): Tarek wants a functional v1 with a good-quality UI (Phases 4–5 as renumbered above) before taking on this more architecturally different feature. Full research from the scoping session, so the next pass doesn't start from zero:

  **The original scope** (`ROADMAP.md`'s old Phase 4 bullet): a chat-style input for one-off requests outside a user's default topics ("what's happening with the Fed today"), appending resulting card(s) to the current feed without disturbing existing cards.

  **A real gap in the docs, worth resolving before building:** this phase's premise (arbitrary free-text queries) sits alongside a separate "Explicitly deferred" entry above, "Free-text topic/source entry (v2)" — the docs never explicitly distinguish the two. They're different features: the deferred entry is about *permanent* free-text entries in a user's saved topic/source preferences (onboarding), not about a *one-off* ad-hoc query. Ad-hoc requests were never actually blocked by that other deferred item — just worth stating explicitly next time, since the overlap reads as a contradiction on a first pass.

  **Why this can't reuse the existing pipeline as originally implied ("runs the same pipeline for that one topic"):** confirmed by reading `src/lib/ingest.ts`, `src/config/feeds.ts`, `src/app/api/digest/route.ts`, and `src/types.ts`:

  - `ingestArticles()` is fundamentally curated-feed-driven — it loops `FEEDS[topic]` (a fixed `Record<Topic, Partial<Record<Source, string>>>` grid), with no fallback for a topic that isn't in that grid. A free-text query like "the Fed" has no RSS feed and would silently yield zero articles.
  - The docs' implied fallback for this — GNews — is **entirely unbuilt**: `grep -rin "gnews" src/` returns zero hits. It exists only as a mention in `TECH_STACK.md`/`ARCHITECTURE.md`, scoped there as a supplement for thin *curated*-topic RSS coverage, never connected to ad-hoc queries anywhere in the docs.
  - `runDigestPipeline`/`POST` in `route.ts` bakes in the curated multi-topic `ingestArticles` call and the "one digest per user per day" identity (`upsertDigestForToday`'s `unique(user_id, date)` constraint) — neither fits a one-off, possibly-repeated-per-day query shape.
  - By contrast, `cluster.ts`, `triage.ts`, `writeCard.ts`, and the new `dedup.ts` are all genuinely topic-agnostic — none reference the curated `TOPICS` union, they just carry `topic: string` through structurally. They'd run unmodified on ad-hoc-sourced articles, if ad-hoc sourcing existed.
  - The `Topic` type (`src/types.ts`) is a strict 13-value union used pervasively (`Card.topic`, `Cluster.topic`, `Article.topic`, and `Feed.tsx`'s `orderTopics()`/tab-rendering, which silently drops anything not in `TOPICS`) — but the DB layer already stores `topic` as plain `text` with no enum/CHECK constraint (`supabase/schema.sql`'s own comment: "Nothing lets a user submit arbitrary free text anyway"), and `digests` already has an **unused `requested_topic text` column** that looks like it was added specifically anticipating this feature, never wired to any code.

  **The recommended reframe, not yet implemented:** don't build a GNews client or force ad-hoc through the curated batch pipeline (ingest → cluster → dedup → triage → write) — that whole shape exists to sift a large multi-source scan down to what's notable, which is moot for a single query the user already decided was worth asking. Instead: one (maybe two) Claude Sonnet call(s) using Anthropic's server-side `web_search` tool (current version `web_search_20260318`, with the `_20260209`+ dynamic-filtering behavior and citations built in) — search live, read cited sources, synthesize directly into a card-style answer in one shot. This sidesteps GNews entirely, doesn't require widening the `Topic` type (the already-unused `requested_topic` column is a natural home for it instead of forcing it into `user_topics`), and doesn't need to fit the one-digest-per-day identity model.

  **Cost estimate for the reframed approach** (not measured, reasoned from Anthropic's published web-search pricing — \$10/1,000 searches — plus Sonnet token rates): roughly **\$0.04–0.05** for a typical single-topic ad-hoc query (~2 searches, ~6,000 input tokens including search-result content, ~500 output tokens), up to **\$0.10–0.20** for a broad/comparative query triggering many searches — worth capping with the tool's `max_uses` parameter. For reference, that's roughly a seventh to a third of the pipeline's own measured **\$0.335** full digest (`TECH_STACK.md`, 2026-08-15) — this being one targeted question rather than a full multi-topic scan. (This comparison used to anchor on a \$0.17 digest, which turned out to be a dev-profile measurement ~10× under the real cost; the *conclusion* survives the correction, but with far more headroom than it originally claimed.) Biggest source of estimate error: Anthropic doesn't publicly document how much page content the tool returns per search result — instrument for real once built, same as every other cost figure in this project.

  **Still open, needs deciding before implementation starts:** where ad-hoc cards live in the UI (`ARCHITECTURE.md` says they're "appended to the existing feed, rather than replacing it," implying inline rather than a separate tab, but no doc specifies exact placement/visual treatment — no existing component in this codebase combines a plain text input with a streaming-fetch submit handler either, the closest precedents are `Feed.tsx`'s `loadDigest`, which streams but has no input, and login/signup's text inputs, which aren't streaming); whether ad-hoc results persist at all (today's digests are per-day persistent and bookmarkable — is a one-off query saved anywhere, part of history, bookmarkable the same way?); rate-limiting/abuse prevention (never addressed anywhere in the original docs, and newly relevant since this is a free-text, user-triggered surface with real per-request cost, unlike the fixed curated topic list); and Haiku vs. Sonnet for the synthesis call (lean Sonnet, to match the product's existing "Sonnet writes what people actually read" quality bar rather than Haiku's triage-tier quality).

- **Dynamically-updated "hot topics" sublists** (raised during Phase 2 scoping, 2026-07-28): a regularly-refreshed list of trending sub-topics within Geopolitics/Tech-AI (e.g. "Middle East gas prices," a specific hot AI company) that users could browse and add to their preferences over time, beyond the fixed curated list. This is a discovery/recommendation feature, not a config change — it needs something to *decide* what's trending (LLM analysis of recent ingested articles, or manual curation), storage, a refresh cadence, and a UI for revisiting/updating preferences post-signup.   **Three things that make this cheaper to do later than it sounds, and one that makes it harder.** Cheaper: the cost pipeline built 2026-09-11 already records per-call, per-stage, per-model spend, so a bake-off is *measurable* rather than argued — generalising `TrackedModel` and the `PRICING` table is most of the instrumentation work, and it is already the shape that wants it. Clustering is local embeddings and touches no provider at all, so the whole first stage of the pipeline is out of scope by construction. And the prompts are plain system+user text with nothing provider-specific in the content. Harder: **there is no provider abstraction in this codebase** — see the portability assessment below — and every call site uses Anthropic's structured-outputs helper, which is the one part that is not a client swap.

  **Do not start this without an evaluation set.** The Final Phase had no ground truth for `triage.ts` and had to fall back on distribution bands (severity ≥ 3 counts) as a proxy, and F.4.6 caught a real calibration drift only because it re-measured. Swapping models re-opens exactly that, on every stage at once, with no way to tell a cheaper model from a worse one. **The per-card relevance-feedback item in Track A is the cheapest route this project has to real labels, and it is effectively a prerequisite for taking this seriously.**

### Provider portability — how coupled is this to Anthropic?

_Assessed 2026-09-14, against the tree at `c61aa10`, because the model-exploration item above is unanswerable without it._

**Honest summary: it was built assuming Anthropic, not built to be portable — but the coupling is concentrated, not diffuse.** Five files and one pricing module hold essentially all of it, and the structurally expensive parts of the pipeline are provider-neutral.

**What is coupled, in descending order of effort to undo:**

- **Structured outputs are Anthropic SDK-specific, and this is the real work.** Every Claude call uses `client.messages.parse()` with `output_config: { format: zodOutputFormat(...) }` and reads `response.parsed_output`. That is an SDK helper, not a wire format. OpenAI-compatible APIs (which is how most Chinese models are served) have analogous JSON-schema modes of varying fidelity — so this is a rewrite of the call layer plus a re-validation of every schema against every candidate model, not a client swap.
- **There is no provider abstraction layer at all.** Five separate `new Anthropic()` clients, one each in `rank.ts`, `triage.ts`, `dedup.ts`, `writeCard.ts` and `cards.ts`. The first step of any switch is introducing the seam that does not exist.
- **Model IDs are hardcoded string literals at every call site, written twice each** — once in the request and once as `recordCall`'s argument.
- **`TrackedModel` is a two-value union** (`usage.ts`) and it is load-bearing in the money path: the collector, the pricing table, the run record, the Supabase `usage_runs` column and the cost report all key off it. Adding a provider widens a type that several correctness guarantees depend on.
- **Usage field names are Anthropic's** — `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`. OpenAI-compatible responses use `prompt_tokens`/`completion_tokens`, so `normalizeUsage` needs a per-provider shape.
- **The pricing model encodes Anthropic's cache economics** (`cacheReadMultiplier` 0.1x, `cacheWriteMultiplier` 1.25x/2x). Other providers price caching differently or not at all.
- **`writeCard.ts` sends `thinking: { type: "disabled" }`** on the Sonnet path, and its comment documents Anthropic's `max_tokens` semantics (thinking and output share one budget). Both are provider-specific.

**What is already provider-neutral and needs no work:**

- **Clustering is entirely local.** `embeddings.ts` and `cluster.ts` call no API. The first pipeline stage is out of scope for any switch.
- **`recordCall` is generic** — `<R extends object>`, duck-typing `.usage` off the response. Only `normalizeUsage`'s field names are Anthropic-shaped, and that is one function.
- **The prompts are plain system + user text.** Nothing in the content is provider-specific.
- **`usageRecord.ts`, `usageSinks.ts` and `costReport.ts` are shape-agnostic** apart from `TrackedModel`.
- **The pipeline architecture itself** — ingest, cluster, triage, dedup, write, rank — carries no provider assumption.

**The practical read:** a provider seam plus one alternative implementation is days of work, not a rewrite, and the cost instrumentation to judge the result already exists. The schedule risk is not the plumbing, it is **quality regression you cannot see** — which is why the evaluation-set prerequisite above matters more than any of this.
