## 2026-08-18 (post-v1, backlog) — two deferred items added to `ROADMAP.md`; the second is a confirmed bug, diagnosed before being written down

No code changed. Tarek asked for two additions to the deferred list, the second conditional on diagnosis actually confirming the behavior. Both are now in `docs/(C) ROADMAP.md`'s "Explicitly deferred (not v1)" section.

**1. Per-card relevance feedback (V2 feature, Tarek's spec).** Relevant / Not relevant on every card; "Not relevant" opens a modal with the pipeline's known failure modes (duplicate in today's brief, story not from the last 24h, wrong information, other → free text), then removes the card from the digest with a reversible undo. Written up with the three design questions that actually gate it — what the feedback table is *for* (telemetry vs. a signal fed back into triage, which decides the schema and can't be cheaply retrofitted), removal semantics (a `dismissed` flag filtered at render, **not** a hard delete — `rank.ts` re-ranks the full cumulative pool every run, so a deleted card can be re-added by a later run as a "new" card, which is worse than the original complaint), and the re-flow question Tarek raised. On re-flow the note points at Phase 8.4's existing `applyRankUpdates` + `pendingEntrances` machinery rather than a new mechanism, since rank 1 renders hero-sized and removing the hero means promoting something into that slot — a problem this codebase already solved once. Flagged the side benefit: the reason picker is the cheapest route to a real labelled eval set for the triage prompt, which the Final Phase never had (it fell back on severity-distribution bands as a proxy for ground truth).

**2. Backgrounded-tab generation leaves cards invisible until reload — diagnosed, confirmed real, added.** Tarek switched browser tabs mid-generation; on return the run had finished but no cards showed until a refresh. Traced through `DigestGenerationContext.tsx`, `NewsCard.tsx`, `entranceTiming.ts` and `motion-dom`'s installed source:

The NDJSON stream isn't rendering-gated, so the `done` event lands and `setCards` runs — **the state arrives; this is not a lost-state bug.** New cards mount at `initial={{opacity: 0}}` and animate up under Motion's rAF frameloop, and **rAF does not fire at all in a hidden tab**. The `pendingEntrances` backstop timer (`DigestGenerationContext.tsx:274-284`) is a `setTimeout` — throttled in a hidden tab but not stopped — so it fires while the animation has made zero progress, clears the batch, and flips `animateEntrance` to false. Motion then `stop()`s a still-running animation, and `NativeAnimation.stop()` (`motion-dom/.../NativeAnimation.mjs:77-91`) returns early only for `idle`/`finished` — for a running one it calls **`commitStyles()` then `cancel()`**, writing the current `opacity: 0` into the element's **inline style** and discarding the animation. Nothing clears it, so the cards stay invisible until a reload rebuilds the DOM from SSR with `animateEntrance` false from the start.

**The part worth remembering: this is the same failure shape the project already hit twice.** `entranceTiming.ts`'s own comment records "a card retired while animating loses its `animate` target and freezes part-faded... precisely the bug shape that broke Phase 8.4 twice." The fix then was a shared constant making the timer strictly longer than the animation — a correct invariant *in wall-clock time*, resting on an unexamined assumption that animation time and wall-clock time advance together. A backgrounded tab is exactly where they don't: one stops dead, the other keeps running. The timer and the thing it guards were never on the same clock; visibility was just hiding it.

Fix direction recorded but deliberately not implemented (Tarek explicitly didn't want work started): pause the backstop on `visibilitychange`, or make the retired state render `opacity: 1` explicitly rather than relying on "no `animate` prop" meaning "whatever the element currently is," or drop the `opacity: 0` initial for an entrance additive over a visible base — the last being most robust because it degrades to "no animation" rather than "no content," the right trade for something purely decorative.

**Honest limit on the diagnosis:** read from code and Motion's source, not reproduced in an instrumented browser. A zero-cost discriminator is recorded in the roadmap item for next time it happens — if the page shows "No edition yet today." with the topic nav disabled, the state never arrived and this diagnosis is wrong; blank space with the nav enabled (it's gated on `hasDigest`) and `opacity: 0` on the card elements in DevTools confirms it.

### The determinism fix (`profile.ts`) — converged clean at round 2

`getUserProfile` read both preference tables with no `ORDER BY`. Postgres guarantees no row order without one and every page re-queries on render, so the topic nav reshuffled between navigations. A module-local `inCuratedOrder(curated, rows)` now walks the curated `TOPICS`/`SOURCES` and keeps what the DB returned, making the result a subsequence of the curated list **by construction** — ordering, stale-value filtering and dedup collapse into one operation that can't disagree with itself. Applied to sources too, because "order doesn't matter there" is a property of today's consumers, not of the function. No SQL, schema or call-site change.

Sequenced **before** the paid run for a narrow reason worth stating precisely: topic array order feeds `ingestArticles`'s job order → the global first-wins URL dedup → which topic a syndicated article is filed under → per-topic cluster counts → batch composition. Measuring a topic-composition-dependent metric against an unstable topic order changes two variables at once. The magnitude is probably small — the nine topics are largely disjoint — and it was shipped because it's a correct fix that had to land anyway, not because it will move 35.7% toward 20%.

`profile.ts` had **no tests at all** before this (all seven route wiring tests `vi.mock` it wholesale), so nine were added. Round 1 found two real things: my test fake defaulted `data` with `?? []`, which coerced an explicitly-passed `null` before `getUserProfile` ever saw it — so the null case could not detect deleting production's own guard, proven by deleting it and watching 9/9 still pass; and a comment claiming the curated order was "not expressible in SQL," which overstates (`array_position` can express it). The real reason is that encoding it in SQL would put the curated order in two places that must be kept in step. Round 2 clean from both agents.

### The triage calibration fix (`triage.ts`) — converged clean at round 10

Two changes. The **prompt**'s batch-contract paragraph now carries a base-rate anchor and a restatement of the "when genuinely torn, reject" tiebreaker, which had been stranded in text written when the model saw one cluster per call. And a **free diagnostic**: the per-verdict log line now names the story. `loggedHeadline`/`loggedReason` are console-only, cost zero tokens, and are what make `TRIAGE_REASONS=0` safe — topic + verdict + severity records that a verdict was reached but never about what, so without titles a reasons-off capture cannot be audited at all.

**Ten rounds. Nine found something real, and the shape of them is the lesson.**
- **R1** — `loggedHeadline`'s docstring claimed a totality the function didn't have. `qa` proved the expensive version: a title getter that succeeds while `clusterContext` builds the prompt (so the call is made **and billed**) and throws on the later log read escapes `judgeBatch` and discards *every* verdict in that response, not just its own — up to 19 good, already-paid-for verdicts back through the retry ladder.
- **R2** — still not total: the `replace`/`trim`/`slice` chain ran *outside* the try/catch. Truncation split surrogate pairs. And the finding that mattered most: **the prompt corrected pass/reject count but said nothing about severity**, while F.4.6's own data showed the severity distribution drifting and the newly-chosen primary metric is severity-based. Without R2 the paid run would have measured a half-fixed prompt against a criterion the fix didn't address.
- **R3, R7, R8** — three separate instances of one shape: *the code is right but the guarantee isn't pinned*. Narrowing `loggedHeadline`'s guard back left the suite green at 403/403; `loggedReason` had zero totality tests, so deleting its guard outright left every test passing; and `loggedReason` lacked the transform-throw test its twin had. Each was a real hole in what the tests could detect, not a bug in what the code did.
- **R4, R6, R9** — a survivable assertion (`toContain("typical day")` survived deleting the entire anchoring paragraph, since the phrase appears in three other places); an unbounded `reason` field while the title was capped, on the field *more* likely to overrun since its 12-word limit is only a prompt instruction; and a missing whitespace-only-title test.
- **R5** — the `reason` segment got none of the title's normalization, so an embedded newline in unconstrained model output would split one verdict across two apparent `[triage]` lines — corrupting exactly the capture a reasons-on run produces. Fixed by extracting `flattenForLog(value, maxPoints)` and giving both fields the same treatment.
- **R10** — clean from both.

**One reviewer finding was rejected after checking it.** R6 argued the `loggedReason(verdict: object)` parameter type was unnecessary because missing optional properties are assignable. Verified against `tsc` with a minimal repro instead of reasoning from structural-typing intuition: it does not compile. A type whose properties are all optional is a **weak type**, and TypeScript rejects assigning something sharing none of them (TS2559) — the verdict union's reasons-off arm has no `reason` key, so it shares nothing. The comment was reworded to name that rule rather than describe it loosely. Worth recording that an agent's confident, well-argued finding was wrong and the compiler settled it.

### Deferred, raised here so they reach `ROADMAP.md` in the doc pass

- **`cluster.test.ts` has order-dependent flakiness** — a shared mock not reset between tests; fails on roughly half of shuffled seeds. Unrelated to this work, found while checking that the new prototype-tampering test doesn't leak.

Publishing the cold-start figure unqualified would over-size V2.0's cap by ~2× — the same class of error as the original 10×, in the safe direction.

## 2026-08-13 (Final Phase, F.4.4) — the since-cursor now carries across days; eight review rounds, six of them finding something

**The bug F.3 identified, fixed.** `upsertDigestForToday` returned *today's* row's `last_generated_at` as the pipeline's since-cursor, so every new day started null, fell through to ingest's 48h fallback, and re-covered stories the previous day's digest already had. Cross-run dedup couldn't catch them either — it only compares against today's cards, and on a new day there aren't any. Now `getLatestGeneratedAtForUser`: the newest qualifying `last_generated_at` across **all** of the user's rows. `upsertDigestForToday` returns `{ digestId }` only — the cursor is a property of the user, not of a row, and conflating those was the bug.

`FIRST_RUN_LOOKBACK_MS` → `LOOKBACK_CEILING_MS`, a ceiling rather than a fallback: `cutoff = max(cursor, now − 48h)`. New user gets 48h; someone back after a week gets 48h, not seven days of backlog. The route's dedup gate moved from `sinceIso !== null` to `existingCards.length > 0` — the old proxy only coincided with "there is something to compare against" because the cursor reset at midnight, and a cross-day cursor breaks that coincidence. Also deleted the comment blaming "the browser's localStorage was cleared," which was never the mechanism.

**Two guards in the query, both load-bearing rather than defensive.** `.not("last_generated_at", "is", null)` — Postgres sorts NULLs *first* under `DESC`, so today's freshly-created row would win the ordering and hand back null, reinstating the exact bug. `.lte(plausibleCursorLimitIso())` — this is a MAX query: it returns one row and discards every other timestamp before any caller sees them, so a single corrupt far-future value would win **forever** and the legitimate next-most-recent cursor would be unrecoverable downstream. Not hypothetical for this database: `qa` agents have inserted synthetic digest rows directly, and one seeded row can't be deleted (no DELETE policy on `digests`).

**The future-cursor decision, and why it isn't uniform.** A cursor ahead of the clock splits in two. Within 5 minutes it's honoured — ordinary skew, and the run finding nothing is the truthful answer to "what's new since a moment ago." Always falling back instead would be actively harmful: a writer running seconds fast would make *every* run see a future cursor, fall back, and re-ingest 48h — a permanent duplicate storm at ~10× cost, not a one-off. Beyond 5 minutes it's corrupt: discarded for the ceiling, with a guarded `console.warn`. The threshold lives in a new `src/lib/cursor.ts` shared by the query and the consumer, because drift between them is silent — the query would accept a value the consumer then discards.

**Self-caught mid-verification (not found by either agent's own testing):** while live-verifying that fix by reproducing the exact focus-mode round-trip scenario, found a second, more serious bug. The fix's `measure()` used `getBoundingClientRect()` on the summary/footer elements — but `NewsCard`'s outer wrapper shares a Motion `layoutId` with `FocusOverlay.tsx`, and closing focus mode plays a ~0.4s shared-element `transform`-based return animation back down to the grid cell. `getBoundingClientRect()` reports the *visual* (transform-inclusive) rect, so the synchronous initial `measure()` call — firing the instant the real face subtree remounts, right as that return animation starts — captured a wildly inflated reading. Live-reproduced repeatedly: a card's clamp corrupted to 17-18 lines instead of the correct 9, and **stayed wrong forever**, since `ResizeObserver` only fires on real layout-box size changes, never on `transform` animations, so nothing ever corrected it — confirmed by polling for 3+ seconds with zero recovery, well past the animation's own duration. This is worse than the original symptom: not frozen-but-valid, but frozen-and-wrong, meaning a user who ever opened focus mode on a card would see it overflow afterward. Root-caused via a temporary debug build of the hook (logged every effect run / measure call / observer attach-disconnect) rather than guessing. Fixed by switching the measurement from `getBoundingClientRect()` to `offsetTop` (`footer.offsetTop - summary.offsetTop`) — the untransformed layout-box position, valid throughout any transform animation since `summary` and `footer` are direct children of `face` (their shared `offsetParent`, itself `position: absolute`), unaffected by transforms on `face` or any ancestor.

## 2026-07-28 — Fixed a real memory-crash incident: unbounded embedding batch size

Tarek hit a serious one testing locally: created a new account, selected a large topic/source set, clicked "give me today's news," and 10+ minutes later it was still stuck on "grouping 1193 articles into stories" — with Activity Monitor showing `next-server` pulling 40% CPU and, worse, ~34GB of memory, slowing his whole machine down. Killed the stuck process (it had actually already died on its own by the time the kill landed, likely OOM).

First hypothesis (unbounded article snippet/content length feeding the embedder) was wrong, and cheap diagnostics ruled it out fast: real ingested data for the full 13-topic × 46-source selection showed a mean text length of 347 characters and a max of 6698 — nowhere near enough to explain gigabytes of memory on its own.

Real cause: `src/lib/cluster.ts`'s `embed()` sent the *entire* article set (1230 articles at this scale) to the local transformer model in one single batched call. Transformer batch inference pads every sequence in a batch to match the longest one, and attention memory scales with roughly `batch_size × longest_sequence²` — so one large batch combined with even a single moderately-long outlier article is enough to blow memory up catastrophically. This was invisible at every scale tested earlier in this project (Phase 1's 2-3 topics, or the deliberately-small subsets used in Phase 2's own verification passes) and only surfaces at real-world scale, which nothing had exercised until now.

Fix: chunked the embedding calls into bounded batches (64 articles per call, looped) instead of one unbounded batch — caps peak memory to one chunk's worth regardless of total digest size. Also corrected a now-stale code comment that claimed digests only ever see "dozens, not thousands" of articles — with no cap on topic/source selection, they genuinely can.

Verified carefully given the severity: ran the fix with active external memory monitoring (a kill switch armed at 8GB) rather than blindly re-triggering the same crash. Moderate scale (8 topics, 497 articles) peaked at 2.4GB; the exact full-scale scenario that crashed the machine (13 topics × 46 sources, 1232 articles, 972 clusters) peaked at **4.1GB** and completed in 35 seconds — down from an unbounded climb past 34GB and an eventual crash.
