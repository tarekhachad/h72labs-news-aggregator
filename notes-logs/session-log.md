The grid-packing fix went through **3 full qa/code-reviewer rounds**, and the implementation was rebuilt twice within that process — worth logging in detail since it's a real example of the iterate-to-convergence rule catching increasingly subtle bugs in the same function:

- **First implementation** (an explicit JS pre-pass replacing CSS `grid-auto-flow: dense`, computing literal grid positions via a cell-by-cell occupancy bitmap, widening the last card placed in a row to close any leftover width): round 1 found this left a **mid-row hole** when input arrived out of tier order (e.g. a small before two heroes) — the row-closing logic only ever widened the last item *actually placed* in a row, and a taller item's second row could bleed into a row nothing was ever placed in directly. - **Round 2** (targeting that fix) found a second, structurally distinct gap: even with correctly tier-ordered input, whenever a rowSpan-2 card's first row got *exactly* consumed by trailing rowSpan-1 cards, its **second row** was left uncovered — a CSS grid item can't be widened on only one of the rows it spans without overlapping different content already sitting in the other row. Both `qa` and `code-reviewer` independently converged on the identical root cause and reachable counterexamples (`hero+medium`, `hero+small`, `large+medium`, `large+small` — all just 2 cards, not contrived).
- Given two structurally similar bugs from the same patch-a-special-case approach, **the function was redesigned rather than patched a third time**: items are stable-sorted by tier, then packed into a strict sequence of "bands" — a run of same-rowSpan cards filling a fresh, exclusive set of rows, closed by widening its last card before the next band starts. Since a band never shares a row with a different-rowSpan band, the root cause of both prior bugs (cross-rowSpan bleed-through) can't occur at all — gap-free by construction, not by special-casing.
- **Round 3** (fresh, both agents, against the redesign): `code-reviewer` traced the "gap-free by construction" claim line-by-line (widen math, empty-band risk, infinite-loop risk, stable-sort reliance) and found it genuinely sound, but surfaced a real design trade-off: the band model can leave a lower-ranked card (e.g. rank 3 on a full 6-story front page) alone in its own row-span-2 band, widened to full page width *and* full hero-height — a visible hierarchy inversion versus the actual rank-1 hero, and not a rare case (it's what a full 6-pick front page produces routinely). `qa` independently fuzzed 3,500+ random tier sequences plus a live-generated real digest and found no correctness bugs either. ## 2026-07-28 — Fixed a real memory-crash incident: unbounded embedding batch size

Tarek hit a serious one testing locally: created a new account, selected a large topic/source set, clicked "give me today's news," and 10+ minutes later it was still stuck on "grouping 1193 articles into stories" — with Activity Monitor showing `next-server` pulling 40% CPU and, worse, ~34GB of memory, slowing his whole machine down. Killed the stuck process (it had actually already died on its own by the time the kill landed, likely OOM).

First hypothesis (unbounded article snippet/content length feeding the embedder) was wrong, and cheap diagnostics ruled it out fast: real ingested data for the full 13-topic × 46-source selection showed a mean text length of 347 characters and a max of 6698 — nowhere near enough to explain gigabytes of memory on its own.

Real cause: `src/lib/cluster.ts`'s `embed()` sent the *entire* article set (1230 articles at this scale) to the local transformer model in one single batched call. Transformer batch inference pads every sequence in a batch to match the longest one, and attention memory scales with roughly `batch_size × longest_sequence²` — so one large batch combined with even a single moderately-long outlier article is enough to blow memory up catastrophically. This was invisible at every scale tested earlier in this project (Phase 1's 2-3 topics, or the deliberately-small subsets used in Phase 2's own verification passes) and only surfaces at real-world scale, which nothing had exercised until now.

Fix: chunked the embedding calls into bounded batches (64 articles per call, looped) instead of one unbounded batch — caps peak memory to one chunk's worth regardless of total digest size. Also corrected a now-stale code comment that claimed digests only ever see "dozens, not thousands" of articles — with no cap on topic/source selection, they genuinely can.

Verified carefully given the severity: ran the fix with active external memory monitoring (a kill switch armed at 8GB) rather than blindly re-triggering the same crash. Moderate scale (8 topics, 497 articles) peaked at 2.4GB; the exact full-scale scenario that crashed the machine (13 topics × 46 sources, 1232 articles, 972 clusters) peaked at **4.1GB** and completed in 35 seconds — down from an unbounded climb past 34GB and an eventual crash.
