## 2026-07-30 — Made writeCard's truncation check non-fatal on false positives

Follow-up to the same-day `writeCard` diagnostic fix: adding `stop_reason` to the log only made false positives *visible*, it didn't stop them from still dropping a good card. Tarek asked to fix that properly instead of waiting to observe it.

Changed `writeCard.ts`'s decision logic: an empty/whitespace-only summary always throws (new safety net — covers a refusal or parse-failure producing no real content). Otherwise, if the summary doesn't end in terminal punctuation, it only throws (drops the card) when `stop_reason` is confirmed **not** `"end_turn"` — i.e. an allowlist of the one known-safe completion state, not a denylist of just `"max_tokens"`.

That allowlist-vs-denylist distinction came from the `code-reviewer` subagent pass, independently confirmed by `qa`'s test suite: my first version only special-cased `max_tokens` as "drop it," which meant `stop_reason: "refusal"` (a real Anthropic stop reason for policy-blocked responses) would have fallen through to "keep it" — exactly backwards, since a refusal's text can be short and non-empty ("I can't help with that") without being a truncation. Fixed by flipping the condition to only trust `end_turn` specifically. Also applied the review's minor log-truncation suggestion (cap the logged summary text at 200 chars).

Verified via a throwaway logic-mirroring script (empty summary, bad-punctuation+max_tokens, bad-punctuation+end_turn, bad-punctuation+refusal, good-punctuation — all correct) since forcing a real Sonnet call into a specific stop_reason isn't practical on demand; `qa` separately verified the same branches by mocking the Anthropic SDK and calling the real `writeCard` function directly (11/11 passed), which is stronger evidence than my mirrored-logic script alone. Both `qa` and code review flagged the same fundamental, pre-existing scope limit as a non-blocking note: `stop_reason: "end_turn"` only means the model believes it finished — it can't catch a well-formed-looking response that's still substantively wrong (wrong language, off-topic, self-truncated without hitting the token limit) at least given it's a surface-form check only. That's out of scope for this fix, not a new gap it introduced.

## 2026-07-28 — Fixed a real memory-crash incident: unbounded embedding batch size

Tarek hit a serious one testing locally: created a new account, selected a large topic/source set, clicked "give me today's news," and 10+ minutes later it was still stuck on "grouping 1193 articles into stories" — with Activity Monitor showing `next-server` pulling 40% CPU and, worse, ~34GB of memory, slowing his whole machine down. Killed the stuck process (it had actually already died on its own by the time the kill landed, likely OOM).

First hypothesis (unbounded article snippet/content length feeding the embedder) was wrong, and cheap diagnostics ruled it out fast: real ingested data for the full 13-topic × 46-source selection showed a mean text length of 347 characters and a max of 6698 — nowhere near enough to explain gigabytes of memory on its own.

Real cause: `src/lib/cluster.ts`'s `embed()` sent the *entire* article set (1230 articles at this scale) to the local transformer model in one single batched call. Transformer batch inference pads every sequence in a batch to match the longest one, and attention memory scales with roughly `batch_size × longest_sequence²` — so one large batch combined with even a single moderately-long outlier article is enough to blow memory up catastrophically. This was invisible at every scale tested earlier in this project (Phase 1's 2-3 topics, or the deliberately-small subsets used in Phase 2's own verification passes) and only surfaces at real-world scale, which nothing had exercised until now.

Fix: chunked the embedding calls into bounded batches (64 articles per call, looped) instead of one unbounded batch — caps peak memory to one chunk's worth regardless of total digest size. Also corrected a now-stale code comment that claimed digests only ever see "dozens, not thousands" of articles — with no cap on topic/source selection, they genuinely can.

Verified carefully given the severity: ran the fix with active external memory monitoring (a kill switch armed at 8GB) rather than blindly re-triggering the same crash. Moderate scale (8 topics, 497 articles) peaked at 2.4GB; the exact full-scale scenario that crashed the machine (13 topics × 46 sources, 1232 articles, 972 clusters) peaked at **4.1GB** and completed in 35 seconds — down from an unbounded climb past 34GB and an eventual crash.

Tarek separately asked whether triage calls (already parallelized via `Promise.all`, not sequential) should be parallelized further via subagents — clarified that "subagents" (this coding session's Agent tool) has no equivalent at the deployed app's runtime, and flagged the real adjacent risk instead: at 300-500+ clusters, `Promise.all`'s *unbounded* concurrency could trip Anthropic rate limits, and since triage failures are already silently treated as "not notable" (by design), a wave of rate-limit errors would make real news vanish with no visible error rather than crash loudly. Deferred fixing that — explicitly out of scope for this pass, revisit later.

## 2026-07-28 — Phase 1 revisit: real-user testing found and fixed 6 issues
